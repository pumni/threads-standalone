# Product direction — two independent Threads operating lanes

**Owner product decision (2026-10-13; Browser development clarified).** This is the canonical **product-intent and delivery-priority** reference. Browser automation and the official Threads API are two permanent, independent product lanes, not fallback/cutover stages. This file does not grant implementation/file ownership, real-account access, live remote effects, publication or merge authority. Browser code development does not require a platform Terms verdict or official API App Review. Follow [AGENTS.md](../AGENTS.md), the current feature handoff and applicable technical/account safeguards.

## Non-negotiable product decision

Build **two durable, independently usable operating lanes**. Browser is itself an automation tool (search/scroll/read/watch and controlled UI workflows), not merely a manual bridge. The Browser lane never depends on official API tokens, endpoint scopes or App Review, nor on a recurring Meta Terms/compliance approval cycle to design, code, test or ship source-only capabilities. Official API work independently observes its endpoint/token/access requirements; neither lane gates the other's development.

| Browser lane — independently operable | Official API lane — independently operable |
| --- | --- |
| Local headed Playwright/Chromium, account-isolated browser profiles and locks, browser-specific UI discovery, exact-post inspection, and browser-only workflows | Documented official Meta Threads endpoints, endpoint-specific scopes/token management, authorized API reads/writes, API-specific observation, approval and reconciliation |
| Browser search/feed/detail observations, recruiter-vacancy classification, private browser archive/watch/export, topic monitoring and human-reviewed nurturing | API discovery/observation, qualification, API content/review, exact authorized action, journal/readback/report and API-specific CLI |
| Manual browser navigation and operator-provided input remain useful even when automated UI collection is forbidden | May proceed without installing or starting Chromium; cannot assume search/publish scopes are approved |
| **Never requires an official API token, App Review success, API-AUTO availability, API observation, or API journal to start its permitted workflows** | **Never requires a Chromium profile, browser search/reader, browser archive or browser permission to start its permitted workflows** |

These lanes are separate in **runtime entrypoints, access permissions, source provenance, execution lifecycle, effect authorization, failure states, operational acceptance and delivery milestones**. No mandatory combined pipeline, source promotion, shared campaign controller, synchronized state or automatic API substitution. Reusing genuinely pure, side-effect-free normalization/classification helpers or compatible local account metadata is allowed where it does not create a runtime dependency or mix authoritative source/effect state. Browser vacancy records are not official API objects; API observations must not be labelled `BROWSER_UI`. Do not silently merge the Browser Jobs `job_vacancies_v1` archive into S6/S11A candidate queues or API/Nurture journals.

There is **no automatic API cutover or browser deprecation**. Older roadmap wording in [#47](https://github.com/pumni/threads-standalone/issues/47), [#57](https://github.com/pumni/threads-standalone/issues/57), [#64](https://github.com/pumni/threads-standalone/issues/64), or [#66](https://github.com/pumni/threads-standalone/issues/66) is historical when it conflicts with this decision. Their valid account security, compatibility, bounded-operation and scoped technical UAT requirements still apply; a historical demand for generic Meta Terms approval is not a prerequisite to implementing Browser features.

## Browser user journey — end-to-end outcome, not isolated helpers

The browser product should eventually let an operator do the following through documented, usable CLI/workflows **without requiring the official API**:

1. **Select account and browse.** Choose an existing authorized local alias/UUID and isolated Chromium profile, open headed Chromium, log in through the official UI and manually navigate as needed. Preserve locks and never copy credentials/cookies between profiles. **Owner has already exercised opening Chromium and manual browsing in an earlier local test**; do not send the owner back to this as the next development milestone. This owner report is not proof of a new build's live UAT or identity attestation.
2. **Discover browser content.** Given operator-chosen Vietnamese recruitment keywords/topics, perform bounded search/feed navigation and scrolling, identify visible candidate post permalinks, and inspect exact post details. Implement the full automated Browser search/scroll/visible-post reader and connected CLI now, without a Meta Terms/App Review checkpoint. The installed live source currently remains technically disabled; a separate explicitly scoped implementation and operator-run UAT can enable it without reopening generic Terms reviews. Report the actual implementation state accurately.
3. **Attribute and extract conservatively.** Bind the same root card's permalink, actual author and visible own-body text. Distinguish quote/reply/sidebar/hidden or truncated content, uncertain author, missing data and changing targets. Separate **employers advertising vacancies** from job seekers and unrelated content; extract only supported role/company/location/headcount/salary/requirements/apply/contact evidence, with field-level provenance and `PARTIAL`/`UNKNOWN` as warranted.
4. **Archive, watch and retrieve.** Reuse the established Browser Jobs parser, account-scoped private vacancy archive, dedupe/revisions, bounded foreground watch, checkpoints, safe restart/STOP, JSON/CSV export and clear user-readable review/list commands. Do not replace them with a second parser/store/watch engine. Keep sensitive contacts private and subject to separate data-use/retention rights.
5. **Observe topics and support nurturing in the Browser lane.** Rank genuinely relevant opportunities, prepare explainable shortlists and human-reviewable original content/reply suggestions, record local review/follow-up and provide manual native-UI handoff where permitted. Browser-only relevance, editorial workflow and reporting must not require Nurture API credentials or API-AUTO dispatch. No fabricated engagement, automatic likes/follows, spam, or unapproved UI send.
6. **Make operation understandable.** Document exact Windows commands, setup, outputs, failure/STOP/recovery, limits and privacy boundaries. Demonstrate the installed CLI and resulting private records, not merely isolated test helpers. An optional browser launcher or packaging feature must not depend on the API-AUTO executable.

The **core browser vacancy feature** comprises steps 2–4, with step 1 already having a basic implementation/manual owner exercise. Topic nurturing (step 5) and customer deployment polish (step 6) are further browser-specific capabilities; do not claim all are done because vacancy parsing works.

### Browser input modes and operational boundaries

- **Manual headed navigation / operator-supplied data**: distinct from automated collection. Keep a usable browser-only path for the person who directly visits Threads and provides authorized text/permalinks; classify this input with its honest provenance and completeness. Local file/clipboard input can be built and tested offline without enabling automated web collection.
- **Synthetic Chromium HTML / fake browser sessions**: implement and verify complete code paths using local content only; block external requests, use fresh synthetic roots, never touch customer profiles or promote fixtures to real `BROWSER_UI`.
- **Automated real Threads UI search/read/store**: this is intended Browser functionality, independent of official API access or App Review. No recurring Meta Terms determination, express-permission evidence, or #64/#103 signoff is a Browser development prerequisite. The *currently installed* `--source browser` remains technically disabled until the separate live integration and operator-selected account/UAT task is implemented and verified. Do not mistake an offline fixture for live evidence or claim endorsement by Meta.
- **Any post/reply/like/follow or other remote effect**: a separate capability and explicit operator authorization, actor/target/final-text review and action bounds. Observe/review code never silently dispatches; unknown effect outcomes block retries. No stealth, CAPTCHA bypass, private GraphQL/XHR scraping or engagement farming.

**Independent delivery states:** `COMPONENT_PRESENT` (code exists); `SYNTHETIC_E2E_VERIFIED` (installed real entrypoint exercises local Chromium/fakes through archive and observable output); `MANUAL_OPERATOR_VERIFIED` (specific permitted human-guided action was exercised, without equating it to automated collection); `AUTHORIZED_LIVE_VERIFIED` (the operator-approved real account/operation passed scoped private UAT; this is technical evidence, not a declaration of Meta endorsement); `CUSTOMER_RELEASE_READY` (separate security, licensing, packaging and operational evidence). Never infer one state from another.

## Coordinator and new-agent continuity

When taking over a new ChatGPT/Lead session, **do not rely on conversational memory**. Before making a plan, claiming completion, or assigning Codex:

1. Read this document, [AGENTS.md](../AGENTS.md), [CONTEXT_MAP.md](CONTEXT_MAP.md) and the exact current `main` SHA; inspect only the currently relevant code/PRs/issues.
2. Check the owner-reported completed manual browse milestone so it is not assigned again. Verify **actual** state of BF-03 (#160/PR #162) and B2 (#106 + #109), API-AUTO (#71/PR #158), plus the current owned worktree/file leases. A missing remote PR does not prove there is no local Codex work.
3. State: **(a)** what the operator can do now, **(b)** what the next complete runnable workflow will deliver, **(c)** what is still synthetic, **(d)** the exact independently gated live actions. Never claim fake success as live Threads evidence.
4. Coordinate the smallest number of **feature-complete E2E** changes; use explicit nonoverlapping leases and existing parsers/stores/watch/CLI. Do not generate more plan-only issues because a product requirement already has an accepted handoff. Keep API and browser independent.
5. The **current Lead Agent** owns BF-03's acceptance record and any regression follow-up; PR #162 has merged. This product direction document does not authorize another agent to revise BF-03 code or retroactively claim its acceptance.
