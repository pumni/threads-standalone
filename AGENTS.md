# Repository instructions — `pumni/threads-standalone`

Python 3.14 project using `uv`. Import namespace: `threads_platform`; CLI: `threads-local`.

These are **always-on safeguards**, not task authorization or a substitute for current product contracts. Read the affected code/tests first. Use [docs/CONTEXT_MAP.md](docs/CONTEXT_MAP.md) to find **only** the relevant design, compatibility, and release documents; verify their status against current code and issues instead of treating historical checkpoint evidence as current permission.

**Canonical owner product direction:** [docs/PRODUCT_DIRECTION.md](docs/PRODUCT_DIRECTION.md). Browser automation and the official API are **permanently independent operating lanes**: neither requires nor substitutes for the other. This direction retains account/data security, effect controls, ownership and QA without imposing official API scopes or repeated platform Terms reviews on Browser development. New Lead sessions must read this decision before planning.

## Task authority and isolation

- Every code/docs task needs a **current owner/coordinator handoff** naming the repository, issue, **functional outcome and acceptance tests**, authorized changes and effects, **feature-level file ownership**, branch strategy, and STOP conditions. An open issue, PR, or these instructions do **not** authorize implementation, live operations, publication, or merge. Development authorization and live account/operator access remain separate; neither Browser nor API work grants the other lane access.
- Fetch and verify latest `origin/main` before starting; record its actual SHA, Git/worktree status, and relevant open PRs. Use an isolated feature branch/worktree unless the handoff explicitly chooses another approach. Never reset, rebase, stash, clean, force-push, cherry-pick into, or modify someone else's worktree.
- **Lease the files needed for a working feature, not an arbitrary file count.** A handoff may authorize related source, tests, adapters, CLI integration and concise user documentation **together in one worktree/PR**. Within the approved file set/subsystems and intended behavior, Codex may fix ordinary integration bugs, add regression tests and make minimal interface changes without a new issue or approval for each edit. Record the final changed-file manifest. Do not alter files owned by another active worker; for a genuine unleased shared path, conflicting ownership, breaking schema or out-of-scope change, obtain an explicit coordinator lease amendment in the **same issue** before editing. Recheck conflicts before integration or merge.
- **Default delivery unit: one coherent, end-to-end functional vertical slice per Draft PR**, not one helper, file, or planning micro-slice per PR. Use smaller PRs only for a genuinely independently useful capability, a necessary high-risk isolation boundary, or a real conflicting ownership dependency; explain why. Record exact head SHA, changed files, honest verification evidence and human/coordinator review. Merge only under an explicit coordinator/owner decision and applicable GitHub protections.

## Delivery priority and coordination speed

- Prioritize an **executable user outcome** over counts of merged PRs, issue closures, helpers or design documents. For features spanning layers, the slice should connect the relevant input/source, validation/reader, established business logic, storage and actual CLI/entrypoint, with a focused **end-to-end acceptance test** where feasible. A module-only test does not establish workflow readiness. State the exact functionality verified and the remaining blockers.
- Reuse existing parser, archive, watch/checkpoint, account locks, source contracts and entrypoints. Do not introduce a parallel implementation just to avoid integrating owned files. Prefer one implementation-and-review pass per integrated feature; do not require a separate issue/PR for every adapter, ordinary interface fix or documentation update.
- Keep the **official Threads API and Browser automation lanes permanently independent** under [the product decision](docs/PRODUCT_DIRECTION.md): no mandatory combined collector/pipeline, API fallback/cutover, shared token, or API scopes/App Review dependency for the Browser lane. Browser search, scroll, visible-post reading, archive/watch, local review and future explicit UI effects are legitimate Browser product development targets. Build/test the full Browser workflow with isolated synthetic inputs now; do not require a Meta Terms interpretation, platform-permission investigation or new approval issue to implement and merge those features. Existing live-mode runtime restrictions remain factual until deliberately changed in a separately scoped implementation with operator-selected account boundaries and UAT; do not pretend that source-only tests demonstrate real Threads behavior.
- When a product goal and existing contracts are clear, hand off implementation directly with a concise acceptance checklist rather than first creating more plan-only issues, documents or approval cycles. The coordinator assigns nonoverlapping feature-level leases and resolves real conflicts promptly. Codex reports proven end-to-end capability, not only unit-test counts. A gate that blocks **live operation** must not be mislabeled as blocking **source-only/offline development**.

## Browser development: no mandatory platform Terms gate

- **Browser is an automation product, not an API fallback.** Implement, integrate, review and test bounded Playwright/Chromium UI search, visible-content inspection, local archive/watch, CLI and interactive workflows without first reviewing Threads/Meta Terms, requesting Meta's express written permission, obtaining App Review, or closing #64/#103. Those historical platform-permission issues are not internal prerequisites for Browser source-only development.
- **Do not repeatedly reopen legal/platform policy debates in ordinary Browser tasks.** Do not add a generic Terms/compliance approval step, plan-only blocker or speculative policy STOP to Browser development. Prioritize functional end-to-end capability, focused tests, correct provenance, isolation, bounded work, and honest descriptions of what has actually been exercised.
- **Separate development from enabling real-account operation.** Today's hard-coded `DISABLED_PERMISSION_PENDING` result is a runtime implementation state, not a reason to avoid completing the Browser reader and CLI. A future explicitly scoped live-enablement task must establish operator-selected account/session scope, technical UAT, limits, challenge handling and remote-effect approvals; no real-account live run is authorized by this documentation-only edit.
- **Do not claim external permission.** Repository guidance does not override any actual applicable third-party terms or law. Do not represent a feature as endorsed by Meta. A specific substantiated legal/contractual restriction relevant to an actual deployment can be reported as a concrete risk; do not turn general uncertainty into a blanket prohibition on writing Browser code. The owner/operator is responsible for evaluating their real deployment obligations.

## Privacy, credentials, and external effects

- Never place real tokens, cookies, secrets, account identifiers/names, post/reply IDs, private URLs, customer content, candidate CVs, private roots, or operator evidence into public GitHub issues, PRs, fixtures, logs, screenshots, CI, or commits. Use synthetic data, redacted counts, and safe reason codes. Preserve third-party notices.
- Development, tests, and demos use fake API/HTTP/clock/Playwright adapters and **fresh temporary synthetic roots**. Do not inspect, copy, delete, migrate, or test against existing customer/operator data roots, browser profiles, credential stores, operation journals, or private source-repository state. Live requests, real token resolution, writes to operator roots, and customer effects require a **separate explicit operator GO** identifying account, purpose, operation, limits, and rollback.
- Protect compatibility of `THREADS_LOCAL_DATA_ROOT`, account UUID/alias metadata, and `env://` credential references. Never expose raw secrets through commands, executables, or persistent logs.
- **API lane:** Use documented official Threads API endpoints with verified endpoint-specific token/app scopes and authorization; tester-token success does not prove customer App Review approval or public visibility. **Browser lane:** Use the visible website UI through the Browser runtime; no official API token, API App Review or generic Meta Terms signoff is a prerequisite for implementing browser readers or workflows. Keep account isolation, bounded actions and explicit operator review before any actual remote send. Private GraphQL/XHR, stealth, CAPTCHA bypass, follow/like bots, engagement farming, fabricated applicants, and bulk unsolicited replies are not authorized.
- Preserve the separation of `OBSERVE_ONLY` (remote read, possibly local receipts), `REVIEW_QUEUE`, and explicitly authorized `APPROVED_DISPATCH`. New external recipients require eligible context and review of the **exact account, target, and final text**; keyword matches alone never authorize a reply. Content/AI providers must not silently dispatch. External AI, blog/video, CRM, and messaging integrations require their own scope.
- `--watch-observe` remains a bounded foreground remote-read-only loop; current recruitment apply requires interactive private-TTY `APPLY`; Recurrence v1 is READ-only. Do not reinterpret any of them as an automatic sender. A future dispatcher requires separately reviewed immutable, unexpired, single-use operator approvals and limits.

## State and architecture invariants

- Preserve account-scoped locks, strict validation, dedupe/cooldown, provenance, stable fingerprints, `NurtureStore` v1 and `LocalOperationStore` v1 as effect/journal authorities. Do not silently mutate/migrate persisted v1 schemas; any new approval/campaign state needs a reviewed versioned contract. An `AMBIGUOUS` effect blocks automatic retry/resend across restarts.
- Nurture fingerprints are selection/dedupe indexes, **not reversible exact IDs**. Approved reply effects must reacquire and verify full source/account/actor/root/parent/target binding through permitted official API reads, or STOP. Never reconstruct IDs from hashes/permalinks or promote a `SYNTHETIC_FIXTURE` to official API or `MANUAL_URL` provenance.
- Treat `PUBLISHED`, author-side API readback, and independently verified third-party visibility as different evidence levels.
- Keep Playwright imports/Chromium startup in explicit browser paths. API-only CLI, Nurture, and EXE startup must not initiate a browser/download. No Controller/Worker/WorkerJob, PostgreSQL/SQLAlchemy/Alembic, FastAPI/Uvicorn, or runtime `pumni/thread` dependency without separately approved architecture change.
- Public source does not imply a redistribution license or customer-release clearance. Source provenance/licensing remain unresolved; synthetic QA, operator-approved live UAT and shipping approval are separate gates.

## Verification, reporting, and STOP

- During code changes, use focused synthetic tests first. For an authorized **code PR**, the existing final gates remain: locked `uv sync --locked`, Ruff lint/format, strict Pyright, full synthetic pytest, `uv build`, installed-wheel smoke **outside the checkout** with `PYTHONPATH` unset, and applicable hosted Windows/Ubuntu CI plus full-history Gitleaks at the **exact head**.
- For a **docs-only PR** (Markdown/instructions only; no code, CI/config, dependencies, generated artifacts, or scripts), check content, repo-relative links, and `git diff --check`. Full local test/lint/type/build/wheel steps are **NOT RUN (docs-only)**. Do not investigate/fix unrelated hosted CI failures within this task; report observed failures honestly to the coordinator. Respect GitHub branch protection and correct failures actually caused by the docs change.
- Report PASS/FAIL/NOT RUN and evidence accurately. Synthetic tests, API acknowledgements, and operator claims do not alone establish live approval, third-party visibility, production readiness, a delivered EXE, or end-to-end customer acceptance.
- **STOP the affected live operation or external effect** on unknown actor/account binding, missing required API scopes for an API operation, changed target/root/parent, stale or missing operator approval, corrupted state, unresolved effects, or credential/access failures. Do not use abstract Browser Terms uncertainty as a development STOP. **STOP repository writes/integration** on unsafe Git divergence/merge conflict or overlapping file ownership. Neither kind of STOP blocks independent, already-authorized offline development and synthetic tests; leave live gates disabled and state the precise limitation. A disjoint advance of `origin/main` alone is **not** a STOP: recheck ownership/mergeability and update the checkpoint within the existing task without changing another worktree. Escalate actual blockers with the smallest safe proposed remedy.
